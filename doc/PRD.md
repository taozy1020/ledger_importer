# 产品需求文档：Beancount 自动导入工具

**版本：0.1（预研稿）**  
**日期：2026-09-26**

> **2026-09-28 方向更新（dev）：** 分类策略以 [研究方向](research-direction.md) 为准。下文原则 3 和第 6 节里的“规则优先、模型次之、LLM 可选”不再指导实现。人工确认、本地优先和不自动提交主账仍然有效。

## 1. 产品定位

面向使用 Beancount 记账的个人用户，提供本地、可审计的账单导入工作台。工具读取用户从支付宝、微信支付、银行和信用卡手动导出的文件，解析交易、建议分类、识别疑似重复记录，供用户审核后生成 Beancount 交易。

产品不承诺“无人值守自动记账”。它承诺减少重复录入，同时让每条生成记录可追溯、可解释、可撤销。

## 2. 用户与核心问题

### 目标用户

- 已维护 Beancount 账本、愿意自行导出平台账单的个人用户。
- 有自己的一套账户树、分类方式、标签和账本文件组织规则。
- 交易来源多，支付宝/微信与银行卡、信用卡之间容易出现重复记录。

### 主要问题

- 同一笔消费可能分别出现在支付平台、银行和信用卡账单中。
- 平台商户名、摘要、类别不稳定；一次性手工归类难以复用。
- 银行格式因发卡行、账户种类、导出方式而异，PDF、CSV、XLSX、EML 等并存。
- 自动生成的复式分录涉及退款、转账、优惠、手续费、外币等情况，单纯填分类不够。
- 直接追加到主账本会引入重复、失衡或错误账户，发现和回滚成本高。

## 3. 产品原则

1. **本地优先**：原始账单、账本、规则和分类数据默认只留在用户设备。
2. **人工最终确认**：自动分类是建议；低置信度、含糊或账务复杂的记录必须进入审核。
3. **确定性优先**：明确规则优先于统计模型，统计模型优先于 LLM；每个建议展示来源与理由。
4. **可回放**：相同输入、规则和版本应产生相同的待审核结果；规则变化可预览影响。
5. **可追溯和不破坏主账**：保存来源文件指纹及行定位，导出到 staging 文件，通过 Beancount 校验后再由用户合并。
6. **格式和个人习惯分离**：解析器描述“账单是什么格式”；个人规则描述“这笔交易如何入账”。

## 4. 典型工作流

1. 用户提供账单文件，来源适配器提取来源记录，保留原字段、行位置和 source ID。
2. 关联器识别跨账单的可能同一经济活动，只添加匹配证据和 link，不丢弃来源记录。
3. 事件解析器依据来源记录识别支出、收入、转账、退款等，并标出已知 posting 与待确认角色。
4. 分类 provider 给待分类事件提供候选；人工审核流程单独记录最终决定，可将确认后的修改转成规则草稿。
5. Beangulp importer/hook 将可审核事件转换成 Beancount entries，由 Fava Import 页面预览、编辑、接受或跳过。
6. Fava 将接受的 entries 写入 `insert-entry` 配置目标；MVP 使用专用文件并验证账本可正常加载，避免直接改写主账本文件。相同来源记录再次导入时保持幂等。

## 4.1 原型切片

首个原型不必先支持全部来源或智能匹配。用现有 CSV 迁移工具的简单字段/账户映射作为行为基准，实现 `legacy_csv` Beangulp importer；其后使用空操作/精确 ID 关联器、只处理普通收入/支出的事件解析器、静态映射，通过 Fava Import 页面人工确认，并配置 `insert-entry` 写入专用账本文件。每一步都经统一接口，后续再替换或增加银行/支付来源和分类 provider。

当前工作区没有包含该 CSV 工具源码；在源码可用前，先按用户描述复现行为并用预期输出做 golden test，不假定能直接抽取其实现。

## 5. 功能需求

### P0：首个可用版本

- 手动导入文件；至少覆盖支付宝和微信账单，并选取一张真实银行卡/信用卡账单验证扩展机制。
- 用 legacy CSV 映射跑通端到端原型；其 scope 是验证模块契约，不替代支付宝/微信来源支持目标。
- CSV、XLSX；对已知 ZIP/EML/PDF 格式，通过专用适配器支持，不要求通用 OCR。
- 统一交易表：日期、金额、币种、方向、来源账户、商户/对手、原始摘要、来源类别、稳定 ID、来源文件和行定位。
- 用户可配置账户映射、默认账户、规则优先级、交易忽略、标签、元数据和输出文件模板。
- 人工审核界面首选 Fava Import 页面；通过 Beangulp importer/hook 生成待审核 entries。支持 `post`、`skip`、`transfer`、`refund`，复杂拆分可留待后续；确认 Fava 对目标流程足够后再决定是否自建审核 GUI。
- 规则至少支持精确匹配、包含/别名匹配、字段条件、优先级、启停和冲突检测。
- 人工修正可生成“规则草稿”，显示匹配条件、目标账户、来源样本及可能影响；必须由用户确认后才启用。
- 跨来源去重建议；匹配不得只依赖金额，需结合日期、币种、账户、商户/摘要，并显示匹配原因。
- 导出 Beancount，运行语法/基础账务校验；不自动改写用户主账本。
- 可重复导入，识别已审核/已导出的稳定来源记录；可撤销最近一次导出或重新生成 staging 文件。

### P1：审核闭环验证后

- 若 Fava Import 页面不满足跨来源关联或规则反馈工作流，开发 Fava extension 或独立本地 Web GUI，提供过滤/搜索/批量操作、来源证据和规则管理。
- 从人工确认账本学习分类；训练集只包括用户确认且账户合法的样本。
- 提供按商户、来源账户、日期窗口等拆分的离线回放指标，支持撤销/回滚规则版本。
- 收入/退款/手续费/优惠/报销/AA 分摊、跨币种交易和多行复式分录模板。
- 本地模型服务接入（如 Ollama 或兼容本地 OpenAI API 的运行时），作为可关闭的建议器。

### P2：按需求扩展

- 新银行/券商 importer 插件、可配置的字段映射模板。
- 收据关联、附件归档、账户余额核对和导入差异报表。
- 可选插件或模板分享；分享前显式排除账户名、交易数据和个人规则。

## 6. 分类器设计要求

- **第一层：用户规则**。规则只匹配稳定、可解释的字段；精确商户别名和支付账户组合优先。高优先级规则覆盖一般规则，冲突时报告而非静默取巧。
- **第二层：本地传统 ML**。用历史已确认交易训练 payee/account 建议；输出候选账户与校准后的可信度。数据量不足时不强行分类。
- **第三层：可选本地 LLM**。只输出受限 JSON 候选，不生成可直接写入账本的任意代码或分录。账户必须来自用户允许的账户集合。
- **兜底**。未知分类进入用户指定的 suspense/未分类账户，保持可检索；绝不把低可信度预测当作确认结果。
- **学习反馈**。手工变更本身不自动改写规则；由工具提出可读的规则草稿，用户审阅、测试影响并确认后才生效。
- **防止回归**。新规则先针对历史已审核样本回放；若原本正确分类大量变化，需提示并要求用户确认。

具体置信度阈值不在预研阶段拍定，应使用匿名化、经用户授权的样本做离线测试，再设置“自动预填”与“必须审核”的不同阈值。无论阈值如何，首版均要求用户确认导出。

## 7. 非功能要求

- 单用户本地运行；默认不需要账户注册、云服务或联网。
- 不保存银行网银凭证，不自动登录银行/支付平台。
- 密码保护账单只在需要时提示密码；不得写入日志或长期配置；临时解压文件在处理后清理。
- 账单和账本文件不进入崩溃报告、分析事件或外部 LLM 请求。
- 文件解析有大小/行数限制，错误给出文件、行号、字段和恢复建议。
- 金额使用十进制定点数或最小货币单位，不用二进制浮点计算。
- 规则与模板有版本号；导入批次可复现并记录解析器版本。
- macOS 优先验证；核心模型与解析层尽量保持跨平台。

## 8. MVP 成功标准

- 对选定的真实样本，所有格式有效的交易均被解析或有明确、定位到行的错误；无静默丢弃。
- 对样本中的重复交易候选给出可解释依据；用户可区分支付平台记录与银行/信用卡清算记录。
- 用户修改一次分类后，可在不改代码的情况下创建、测试并启用个人规则。
- 连续两次处理同一批输入不会重复生成已审核交易。
- 输出通过所选 Beancount 版本的 parser/校验；用户主账本未被程序直接修改。
- 统计规则命中率、分类建议接受率、重复匹配精确率和审核耗时；首版不预设商业化准确率承诺。

## 9. 明确不做

- 自动获取网银/支付账号密码、绕过平台限制或无授权抓取数据。
- 第一版自动提交交易到主账本，或让模型自行决定并提交账务分录。
- 第一版覆盖所有银行和任意 PDF/OCR。
- 默认调用云端 LLM、上传用户账本或训练跨用户共享模型。
- 将界面、规则引擎、导入器和记账输出耦合成一个不可替换的大模块。
